## 1. 需求摘要

构建一个 **测试报告生成 Skill**，使 Agent 在执行测试后能自动完成「执行测试 → 收集结果 → 生成结构化报告」全链路，并提供「解析已有结果」模式以满足 CI 复用场景。

### 核心目标
- **G1**：一条指令完成「执行 → 收集 → 报告」；
- **G2**：报告标准化四大板块 — 摘要 / 失败分析 / 用例明细 / 覆盖率；
- **G3**：支持主流测试框架结果解析（Jest/Vitest JSON、pytest、JUnit XML 兜底）；
- **G4**：默认 Markdown 输出，P1 支持 HTML / JSON。

### 非目标（本期不做）
- 不做测试用例自动生成 / 修复；
- 不做报告在线托管 / Web 服务化；
- 不做多次运行趋势对比（M4 候选）；
- 不做 lint / 安全扫描等非测试报告聚合。

## 3. 开放问题决策（Q1 / Q2 / Q3）

> 说明：当前为「全流水线模式」+ clarify 阶段，按硬性约束禁止阻塞式提问。故对需求文档遗留的 3 个开放问题采取「自主默认决策 + 假设说明」方式固化，后续阶段可基于既有决策推进，无需再次澄清。

### Q1：首期目标项目栈是否以 TypeScript/Node 为主？

- **需求文档假设**：本文档按"以 TS/Node 为主"制定 P0 范围。
- **勘察矛盾**：三仓均无 TS/Node 测试工程，假设无法用仓库实况验证。
- **决策**：**否，首期 P0 不限定单一栈**。P0 范围调整为：
  - Jest / Vitest（JSON reporter）— TS/Node 框架解析（保留，作为高频框架）
  - pytest — Python 框架解析（保留）
  - **JUnit XML — 通用兜底格式（提升为 P0 核心，非降级项）**
- **理由**：JUnit XML 是跨语言事实标准（pytest、maven-surefire、gradle 均可产出），将其作为 P0 兜底可覆盖任意语言项目，避免 Skill 与单栈强耦合。TS/Node 解析器仍按 M1 实现，但定位为「高频框架解析器」而非「主要假设」。
- **影响范围**：FR1.2 P0 清单语义微调（JUnit XML 从"兜底"升格为"P0 通用格式"）；不影响其余 FR。

### Q2：报告是否需要中文/英文双语模板，还是仅中文？

- **决策**：**首期 P0 仅中文模板**。双语模板列为 M2/M3 候选（非本期）。
- **理由**：需求文档与 User Stories 全为中文语境，首期受众为中文开发者/QA。双语会倍增模板维护成本且非关键路径。
- **影响范围**：FR2 报告内容章节文案以中文为准；报告头「生成时间」等字段保留 ISO 格式时间戳，便于跨时区阅读。

### Q3：是否需要将报告自动推送到 IM / 邮件等渠道？

- **决策**：**不做推送**（与需求文档非目标一致，本期维持）。
- **理由**：推送涉及凭据管理、渠道适配、用户授权，复杂度高且需求方已在非目标明确排除。
- **替代方案**：FR3.3 仅返回「报告路径 + 结果摘要」给用户，由用户自行决定是否转发。

## 4. 关键设计选项对比（brainstorming 方案探索）

### 4.1 解析器架构：插件式 vs 硬编码

| 维度 | 方案 A：插件式解析器（Trait/接口抽象） | 方案 B：硬编码 if-else 分支 |
|------|---------------------------------------|------------------------------|
| 扩展性 | 新增框架仅加新插件，符合 NFR5 | 每加一框架改主逻辑，违反 NFR5 |
| 健壮性 | 单插件异常可隔离，降级输出（NFR2） | 一处异常影响全局 |
| 复杂度 | 需定义统一解析 Trait + 注册机制 | 简单，但技术债高 |
| **决策** | ✅ **采用方案 A** | ❌ |

**解析器统一契约**（向后兼容设计）：
- 输入：原始结果文件路径列表 / 原始 JSON 对象
- 输出：归一化结构 `TestResult { summary, suites[], failures[], coverage? }`
- 新增框架 = 新增实现 + 注册，不动既有解析器（满足 NFR5 与自主决策优先级②「契约优先，向后兼容」）

### 4.2 执行模式：前台阻塞 vs 后台任务

| 维度 | 方案 A：前台同步执行 | 方案 B：后台执行 + 轮询（R2 缓解） |
|------|---------------------|-----------------------------------|
| 短测试 | 体验好 | 有调度开销，过度设计 |
| 长测试 | 阻塞主会话，违反 NFR1/超时约束 | 不阻塞，符合 R2 建议 |
| **决策** | 用于解析模式 + 短执行 | 用于长执行（检测到耗时阈值后切换） |

**决策**：**双模式自适应** — 解析模式纯前台；执行模式默认前台（带超时降级阈值），超时或用例数巨大时自动转后台任务并轮询（对应 R2）。

### 4.3 报告生成：模板引擎 vs 手工拼接

| 维度 | 方案 A：模板引擎渲染 | 方案 B：手工字符串拼接 |
|------|---------------------|------------------------|
| 多格式（MD/HTML/JSON） | 模板分离清晰 | 每格式重复逻辑 |
| 可维护性 | 高 | 低，易漏字段 |
| 依赖 | 需引入模板库 | 零依赖 |
| **决策** | ✅ **采用方案 A**（模板分离） | ❌ |

## 5. 设计要点（供后续系分/编码阶段输入）

### 5.1 模块边界（建议）
1. **FrameworkDetector** — FR1.1 框架识别（配置优先 → 特征文件推断）
2. **ResultParser（Trait + 插件）** — Jest/Vitest/pytest/JUnitXML 实现
3. **TestExecutor** — FR1.3 执行模式（前台 + 后台降级）
4. **ReportRenderer** — FR3 模板渲染（MD 默认 / HTML P1 / JSON 伴随）
5. **CoverageAggregator** — FR4.2-5 覆盖率聚合（auto 检测）
6. **Sanitizer** — NFR3 敏感信息过滤（凭据/密钥/环境变量脱敏）

### 5.2 归一化数据契约（TestResult）
```json
{
  "summary": { "total": 0, "passed": 0, "failed": 0, "skipped": 0, "pass_rate": 0.0, "duration_ms": 0, "status": "pass|fail" },
  "suites": [ { "file": "", "cases": [ { "name": "", "status": "", "duration_ms": 0, "error": "", "stack": [] } ] } ],
  "failures": [ { "name": "", "file": "", "error": "", "stack_excerpt": [] } ],
  "coverage": { "lines": 0.0, "branches": 0.0, "functions": 0.0, "statements": 0.0, "low_coverage_files": [] }
}
```

### 5.3 健壮性与降级（NFR2）
- 结果文件格式异常 → 降级输出，缺失项标注「未获取」，不崩溃；
- 字段缺失 → 默认值兜底（duration=0，coverage=null）；
- 解析失败且无法降级 → 返回明确错误诊断（AC4），禁止生成空报告冒充成功（FR1.4）。

### 5.4 安全（NFR3）
- 报告头「执行环境摘要」不得含环境变量/密钥；
- 错误堆栈过滤敏感路径外的凭据（Sanitizer 模块统一处理）。

### 5.5 幂等性（NFR4）
- 同一结果文件多次生成，内容一致；时间戳字段除外（生成时间每次不同）。

## 6. 风险与自审（brainstorming Self-Critique）

| 风险项 | 影响 | 缓解 |
|--------|------|------|
| R1 各框架 reporter 输出差异大 | 解析层复杂 | 已定插件式抽象（方案 A），单框架隔离 |
| R2 测试执行耗时不可控 | 阻塞会话 | 双模式自适应 + 后台任务降级（§4.2） |
| Q1 栈假设与仓库实况不符 | Skill 在本工作区无法验证 | 调整为通用 JUnit XML 兜底为主，不依赖本工作区测试项目 |
| NFR3 敏感信息泄露 | 安全风险 | Sanitizer 模块统一过滤，报告头白名单输出 |
| 框架检测误判 | 命令错误 | 识别优先级 a→b→c，用户显式命令最高优先（FR1.1） |
